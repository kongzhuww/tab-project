# 聊天消息能力契约

本轮是源码层的架构整理，没有部署、重启服务、操作浏览器或访问真实账号/图库/凭据。旧服务兼容路径保留；完整能力声明须以后另获授权升级服务端。

## 单一来源与分层

- `server/private-chat/protocol.json`：公开静态契约，包含schema/protocol、消息类型键表、旧服务兼容标记、格式与限制；不得放地址、凭据或用户数据。
- `server/private-chat/protocol_contract.py`：读取同目录JSON并校验包内契约。只加载静态文件，不接触环境凭据/数据库/网络；向外仅输出明确的公开字段。缺文件或包内格式错误应停止启动，不猜默认值或重置数据库。
- `server.py` 与 `image_policy.py` 从该契约获取实际执行的类型、正文/JSON/图片限制，避免声明和执行各写一份数字。
- `src/chat/chat-contract.ts` 导入同一JSON，消息类型键同时提供TypeScript联合类型与运行时白名单，`system`仅为客户端本地展示类型，不允许通过服务发送。
- `chat-security.ts` 继续负责通用输入与历史归一化；`chat-images.ts` 管源图处理；`chat-image-header.ts` 管有界内联图片的头部尺寸读取。头部检查不是完整解码或病毒扫描，不能替代服务端验证。
- `private-chat-client.ts` 绑定当前服务身份、保存协商结果、入队前检查、最终POST入口检查和旧队列筛选；不是新的传输服务。

本轮只规范消息发送能力。空间、子房间、好友、活动等仍保留原有返回结构检测与授权规则，不声称所有管理API已有统一版本协商。

## 声明与信任边界

`GET /api/v1/sync` 在原有鉴权后返回：

```text
capabilities:
  schema: 1
  protocol: 1
  messageTypes: [text, image, music, bilibili, github, ...]
  imageMimeTypes: [image/png, image/jpeg, image/gif, image/webp]
  limits:
    messageBytes: 262144
    imageMessageBytes: 2097152
    imageBytes: 1048576
    textChars: 8000
    imageMaxDimension: 8192
    imageMaxPixels: 16777216
  imageMessages: 1
  maxImageBytes: 1048576
```

`imageMessages/maxImageBytes`保留给旧客户端。健康检查也可返回这些公开信息，但前端**不以health响应作为身份、权限或发送能力的证明**。

协商只取已校验身份的同步响应，并以origin/父聊天室/UID绑定；配置/身份改变、明确断开或401/403清空能力。同一已认证父聊天室切子房间仍保留服务身份，不让按钮因正常切房反复闪烁。

远端限制必须为正安全整数，有效上限为“本客户端编译时限制与服务声明的较小值”；未知消息类型/图片格式不启用，不能因服务声称支持更大内容就放宽本机限制。schema/协议不兼容、声明格式无效或尚未同步时不提交新消息，但不删除历史和草稿。

## 旧服务兼容

- 同步响应没有capabilities：使用契约中显式`legacy: true`的既有文字/分享类型，图片关闭。
- 仅有旧`imageMessages: 1`：保留已有图片服务兼容；合法maxImageBytes进一步收紧；字段缺省采用既有上限，字段存在但非法则拒绝协商。
- 已出现新版schema/protocol/types/limits字段却不完整或不合法：不偷偷降级成旧服务，不启用发送。
- 新增消息类型时必须显式决定legacy标记；不得因为新前端认识一种类型，就默认旧服务也支持。未来扩展图片格式也须重新审视旧服务格式配置与解码器，不能自动扩大兼容承诺。
- 旧客户端会忽略新字段；默认限制保持原值。但旧客户端未必能自动适应运营者自行收紧的格式/大小，仍须按实际版本验收。

## 用户动作、队列与回执

- 图片和图库发送入口按能力禁用并说明原因；粘贴路径同样检查。静态图按协商大小/尺寸及可编码格式处理，原图不改；不兼容或超限动图仍拒绝，不静默转静态。
- 文字发送返回本机持久入队是否成功；输入框不在调用前先清空。能力不符或存储失败保留草稿，图片预览同样保留。
- 当前房间发送、跨房间分享及最终消息POST入口共用类型、长度、JSON字节、内联图片格式/字节/头部尺寸检查。创建并分享邀请卡前先检查已知消息能力，不能明知不支持还先创建成员邀请。
- 未知/不兼容能力时队列不启动新POST。能力已知但旧队列某条不再符合时，在选取事务内标记既有paused状态，不发请求、不增加网络尝试次数、不删除消息、不伪装成服务端拒绝；内部attempts=5沿用既有暂停标记，不是额外发出5次请求的证明；之后由用户按原目标手动重试。
- 最终POST前再次检查，以覆盖入队后能力变化。其间已被接受的写入不能撤回，失败状态仍受原有lastAttempt/回执与消息ID去重规则保护。
- 暂停或失败不证明旧尝试一定未送达；同步记录仍可作为服务器落盘证明。入队不等于服务器保存，保存不等于成员已读。
- 无数据库版本/键或历史迁移，不改投新房间、不自动重发被暂停记录。旧paused状态继续兼容旧客户端。

## 限制的准确口径

正文上限是既有客户端UTF-16长度检查；Python按Unicode字符计数，客户端对非BMP字符更保守，不等同于字节或可见字形数。JSON限制用UTF-8字节计数；服务端既检查请求体，也检查规范化存储后的消息。Base64增加体积，原图字节上限与消息JSON上限是不同层次。

25MiB本地选图上限、解码保护、同步响应2MiB读取上限、轮询/数据库配额等不是本轮可由远端放宽的消息能力。代理请求体限制也不会因JSON声明自动调整。

## 部署与验证

后续服务升级必须配套提供 `server.py`、`image_policy.py`、`protocol_contract.py`、`protocol.json`；bootstrap只是已有部署工具，不能为升级重新初始化凭据。先备份代码并用SQLite backup API备份活跃数据库，获授权才部署/重启。

本轮验证仅为 `npm run check`、生成后台脚本语法、Python AST解析、JSON语法解析和差异检查。Python只解析源码，没有导入server或执行其数据库/环境初始化；未运行断言/无头E2E或真实API验收。真实旧/新服务互通、严格限制、断网补发及界面效果仍需授权后人工确认。
