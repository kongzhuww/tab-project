# 聊天架构收尾审查

## 结论与范围

本次为源码静态审查及小范围修正，不是双端运行验收、安全认证或正式发布。已有同步/待发/凭据/HTTP/草稿/投影分工无需为了拆分继续新增模块。本轮仅修改原private-chat-client.ts中的入口收尾边界与文档，没有修改UI、SDK、服务协议、数据库格式或线上服务。

未读取真实凭据、连接真实API、操作浏览器/历史/队列记录或执行部署。没有编写或运行断言/无头E2E。下列“核对”均指源码路径，不是故障注入或真实消息测试。

## 本轮发现并修正

### 1. 邀请保存完成后的过期激活

原joinPrivateInvite在等待凭据写入后，直接清认证并切换公开连接配置；等待期间若已断开、重连、选择另一邀请或改变UID/公开连接，旧调用仍可能激活旧选择。

现由同页面invitationActivationVersion标识激活代次：stopPrivateChat会使旧激活失效，保存后再核对代次、当前UID和操作前公开配置身份。过期调用不再停掉新连接或覆盖公开配置，返回固定的“已保存但未激活”提示。

该检查不撤回已经接受的原scope凭据写入，不是跨标签全局锁，也不承诺检测其它页面对同一键的所有凭据变更。真正的激活仍需服务端重新认证。

### 2. 房间管理刷新仍可能只提交半份目录

原saveSharedRoom会先更新rooms，再解析spaces；spaces格式无效时可能已改掉一半目录。

现在先解析本次所有提供的目录字段，再应用；提交前核对配置身份与当前UID，后续字段提交再检查身份。refreshSpaceCatalog也补齐UID及字段间身份检查。这仍是无await的受守卫赋值，不是Vue多对象事务或对已发管理POST的回滚。

### 3. 空间归档完成后的过期导航回退

原archiveSharedSpace在等待目录刷新之后，未再次核对身份便可能执行返回main；也未区分用户是否已在等待期间另选房间/私聊。

现在刷新后重新检查原身份/UID，仅当当前房间仍是操作开始时的选择且已不在目录中，才执行默认房间回退。不替新服务器/新选择做旧操作的导航决定；其它确实已归档的房间仍可由原同步404规则回退。

另移除门面未使用的pendingDeliveryScopes导入，避免误以为已实现所有历史目标的后台发现；未删除底层函数或增加扫描。

## 仍存在的边界，不计作已解决

1. **历史/回执持久化等待**：chat-history/chat-delivery没有全套硬超时策略。底层写入或回执不settle时，批次锁可能继续等待。不能用“释放锁”假报写入成功/撤回，需单独设计存储故障恢复，不能随意重建或清库。
2. **非当前私聊后台补发覆盖**：outbox当前只扫描当前channel及共享房间目录。未使用pendingDeliveryScopes发现所有旧目标；非当前且不在目录中的私聊，不保证后台自动补发。打开原私聊后才会纳入当前目标扫描。本轮未扩成后台全库扫描或跨服投递。
3. **特殊UID的私聊编码兼容**：dmChannelId仍用两个UID及双下划线拼接，服务端按相同分隔符拆成两项，且channel有160长度界限。因此过长UID组合、包含该分隔符的UID可能被拒绝。普通生成UID通常不触及这些条件，但不能宣称所有合法单个UID的组合都可私聊。修正涉及协议与历史scope兼容，不在收尾中擅改编码。
4. **其它响应/字段兼容**：同步页有有界解析，不等于服主管理、所有好友动作与旧本机缓存均有统一运行时Schema；既有字符串字段界限仍需对部署端自定义/Unicode数据核对，不承诺所有旧实现兼容。
5. **跨页/副作用与存储永久性**：没有跨标签/跨设备恰好一次，accepted事务与音乐/通知副作用不可回滚，浏览器冻结不保证硬实时截止，消息仍由服主服务器保存而非端到端加密。
