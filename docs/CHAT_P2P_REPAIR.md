# 历史方案：P2P 隔离与本地保存修复

> **整篇属于旧方案修复记录。** 其中“当前行为/尚未实现/人工验收”均指 P2P 阶段，不能覆盖现行 HTTP 身份认证、服务端落盘、待发队列或好友实现。当前开发先读 [CURRENT_STATE.md](CURRENT_STATE.md)、[CHAT_SESSION.md](CHAT_SESSION.md) 与 [CHAT_HISTORY.md](CHAT_HISTORY.md)；不据此恢复信令/手动握手或执行旧验收。

## 可选信令模式（代码已接入，尚未部署验收）

新增 `server/cloudflare-signaling` 独立 DO 服务及 `ChatSignalPanel.vue` / `chat-signal-client.ts`。群主可创建绑定 UID 的限时成员邀请并撤销；成员和房间由 DO 持久保存。凭证只存在独立本机 IndexedDB；信令房间刷新后尝试重新认证并握手。信令断开时关闭直连、离线名单仅作缓存展示，不作为授权依据。该模式拒绝手动连线码，避免绕过成员认证。手动 P2P 模式仍保留原有边界。

不启用 TURN，不转发聊天内容。部署步骤与安全/恢复限制见 `server/cloudflare-signaling/README.md`。尚未部署到任何云端，不能据此宣称线上自动重连可用。

## 当前行为
- 握手升级为 v2，绑定房间作用域（服务器地址与 roomId）、随机握手 ID、回应接收者。旧连线码拒绝使用。连线码包含房间地址，请只私下分享。
- 切换房间、服务地址、身份、传输模式会销毁已有直连。双方需通过房间邀请进入同一房间后重新交换连线码。
- 数据帧按房间作用域校验；即时消息发送者必须对应握手对端。此校验不是密码学身份认证。
- 禁止自动发送和导入历史批次。新增独立 IndexedDB 发送队列：仅向发送时在线、已被记录为本条消息接收者的对端重试；不会把历史自动发送给新加入者。发送时无人在线的消息仅保存在本机，需要逐条手动发送。
- IndexedDB 为消息存储主路径；按用户、地址、房间隔离。每条消息单独归档，启动与切房加载最近 200 条，更多通过历史按钮读取。旧 localStorage 快照仅保留迁移读取，不删除旧数据。
- 房间联系人持久保存本房间直接连接过的对端，不再将全部好友塞进每个房间。列表不是权威群成员名单；无群主权限模型。
- 发送前先持久化接收者及消息。每轮最多处理 4 个接收任务、间隔至少 10 秒、最多尝试 5 次；重连后仍按原接收者补发。收方归档成功后返回 ACK；发送方按房间、消息 ID、对端 UID 保存回执并展示接收人数，不表示已读。发送失败或无回执显示等待/暂停；可逐条暂停补发（不是撤回），或明确发送给当前在线联系人。
- 同一存储分区的多窗口通过 IndexedDB 事务竞争领取发送任务。确认记录与消息归档是两个独立数据库；断电/存储失败可能出现重复投递，接收界面按消息 ID 去重。不保证 exactly-once，也不保证浏览器持久存储不被清理。
- 本机发现需要双方主动开启，窗口为 60 秒，仅同源同存储分区适用。未连通可手动交换码。握手等待超过 120 秒销毁，需重新生成。

## 尚未实现
- 可选信令模式的真实部署与双端运行验收；TURN 兜底、授权历史分页同步仍未实现。当前有限次数 ACK/重发不是无限离线投递服务。
- 纯手动 P2P 模式没有权威群成员关系、权限或自动 Mesh；A 连接 B、C 不代表 B 与 C 互通。可选信令模式已编写成员授权和逐个直连逻辑，但还未进行网络验收。
- 可靠加密身份认证；不能将用户自报 UID 当作密码学身份。

## 人工验收（不自动操作浏览器）
1. 两端更新后进入同一房间，生成新的邀请/回应码；以联系人在线状态为准，不以提交回应作为成功。
2. 收发短消息，待写入计数清零后刷新：本机记录及房间联系人应恢复，对端应显示离线，需要重新握手。
3. 一端切换房间：旧连接应断开，旧房间消息不应出现在新房间；原消息仍在原房间。
4. 新连入者不应自动收到此前历史；发送时无接收者的消息不应显示为已接收。已入发送队列的未确认消息仅向原接收者补发。
5. 发消息后查看“对方已接收”；收方归档失败不得发 ACK。接收次数到上限应暂停；手动发送只对当前在线联系人操作，已确认的联系人不重复发送。
6. 超大消息、数据库异常、多窗口竞争与多浏览器实际网络仍需人工验收。

验证仅为类型检查与构建，不代表跨网络连通、断电不丢数据或多人群功能验收。
