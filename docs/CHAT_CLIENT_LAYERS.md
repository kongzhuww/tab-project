# 聊天客户端：同步与待发协调分层

本轮只拆分前端源码与运行时所有权，未部署、重启服务、操作浏览器、使用真实消息/凭据或迁移数据库。现有HTTP协议、界面与消息能力契约不变；后续请求/凭据等待与目标校验的加固见下方边界文档。

## 文件边界

| 文件 | 当前职责 |
| --- | --- |
| `private-chat-client.ts` | 保留公开兼容入口、父聊天室认证身份、凭据/HTTP装配、共享目录/好友操作；装配协调器、完整页读取/持久化/投影边界与消息监听/通知适配 |
| `private-chat-sync.ts` | `PrivateChatSyncCoordinator`拥有同步世代、单轮读取会话、忙碌令牌、轮询计时器、错误退避和启动追赶标记；不打开凭据库、发送POST或直接写View state |
| `private-chat-sync-reader.ts` / `private-chat-sync-projection.ts` | 完整纯草稿与已持久页的当前会话投影，时序/兼容/非事务边界见 [CHAT_SYNC_PAGES.md](CHAT_SYNC_PAGES.md) |
| `private-chat-outbox.ts` | `PrivateChatOutboxCoordinator`拥有单页批次锁、8条预算、目的地快照、独立POST/落盘回执和失败分类；不订阅视图取消或负责同步轮询 |
| `private-chat-credentials.ts` / `private-chat-http.ts` | 独立凭据仓储与单次HTTP请求边界，预算/目标校验/敏感错误处理见 [CHAT_TRANSPORT_BOUNDARIES.md](CHAT_TRANSPORT_BOUNDARIES.md) |
| `private-chat-identity.ts` / `private-chat-operation.ts` | 纯身份/键校验与领域内有界等待，不把写入绑定读取slot |
| `private-chat-types.ts` | 目的地、共享目录与消息上下文叶契约；原client继续重导出既有公开类型，调用方不用换入口 |
| `private-chat-errors.ts` | Transport/coordinator共用的HTTP状态与本地能力错误身份；不附带请求、凭据、地址或响应正文 |

协调器通过明确的ports调用领域操作，没有反向import门面、读认证Token或新增自动启动副作用。消息内容仍可能包含用户明确分享的邀请卡；不能把“不直接读取认证凭据”说成不接触任何敏感消息。import/构造不会自行轮询或打开数据库，启动仍由原生命周期入口决定。

后续已提取凭据/HTTP与同步页校验/状态投影；client仍负责父认证、公开动作与链路装配，并非全应用无状态薄壳。未新增全应用响应Schema框架、全局发送服务或跨服务器联系人发现。

## 同步读取所有权

- 父聊天室认证身份仍在门面，由origin/父room/UID约束。同步世代独立，换子房间只停止旧同步，不清空已验证的同父身份；换身份/凭据、明确断开或401/403仍清认证与能力。
- 各轮复用 `core/read-session.ts`，保留窗口visible时25秒、否则20秒的整轮等待预算。配置、凭据读取所包裹的GET、游标、历史提交及回执存储等候可停止等待；不声称撤回已接受的IndexedDB事务。
- 常规轮询保留visible时约2.5秒、否则10秒；visible时请求wait=6。积压追赶和旧轮尚在退场时保留250ms调度。visible是聊天窗口状态，不保证浏览器后台标签实时执行。
- 失败退避公式不变：3/6/12/24秒，连续两次失败后显示连接故障。401/403停止；非main房间404回默认房间，0ms重启任务也受原世代检查，不能重启后来选择的新身份。
- 旧轮finally仅能释放自己的运行令牌，不能清新世代的syncing或计时器。退出读取会话会清理自身signal/计时器/监听，写入侧不使用该signal。
- 每次新世代先把网络追赶视为history，直到hasMore排空才进入live；非零游标不等于已完成启动追赶。瞬时网络重试不另开世代或重放初始历史。
- 原消息scope/channel/sequence/history-live-self上下文、回执去重与通知策略保留。监听回调可能同步切房，回调结束后及共享状态提交前补做current检查；过期任务不继续覆盖新房间。

历史提交和游标仍在原事务内一起保存，不先推进游标。已有同步记录仍可证明本人消息被服务器保存。一起听的静默恢复、去重与音源规则没有换实现，普通通知的原有筛选也没有扩展成新策略。

## 待发写入所有权

- 当前房间发送仍先归档/持久入队，再异步触发独立发送。显式跨房间分享同样先入队，再走独立单次POST与回执；不切换可见房间。
- 队列每批仍最多8条，遍历当前房间与原共享房间目录中的目标；不新增任意离线房间发现或改变目的地选择。每个目标对象做快照，不能随导航改投。
- 批次POST沿用12秒独立传输signal，显式分享沿用15秒；不连接同步读取/窗口生命周期signal。已经发出的POST可继续完成并向原scope记回执。
- 必须收到 `stored === true` 且id匹配才确认服务器保存；缺少、错误类型、超时或回执写入未确认不假报成功，也不等同对方已读。
- 本地能力不符仍paused；HTTP4xx除408/429外仍按原拒绝规则；其它失败仍未确认。失败记录继续受lastAttempt和received保护，不覆盖更新尝试或已有回执。
- 本轮修正批次中途失败的释放顺序：后续扫描/存储失败时，已发出的批次任务仍全部settle后再释放该实例的flushing锁。失败状态写入异常显示真实存储故障，不让单个拒绝的失败记录Promise提前释放整批锁。
- 锁是该协调器实例的批次锁，不是所有分享的全局串行锁，也不是跨标签/跨设备恰好一次；显式分享、其他窗口与服务器仍依赖原消息ID去重和持久队列规则。

无新自动重发策略、回执存储键、数据库版本、历史迁移、原图操作或服务端部署。能力筛选及旧服务兼容仍见 [CHAT_CAPABILITIES.md](CHAT_CAPABILITIES.md)。

## 明确边界与验证

- 协调器没有给所有写入/数据库API新增统一硬超时；后续凭据/HTTP边界已分别加入预算，见CHAT_TRANSPORT_BOUNDARIES.md。历史/待发回执存储仍在原模块；若迟迟不settle，不能为了释放UI就宣称其已撤回。
- 浏览器原生操作、事件循环调度与多窗口竞争不能由静态构建证明。同步页已做有界业务解析；其它管理接口/本机缓存/所有组件输入并未全量迁移为统一运行时schema。
- 本轮只执行类型检查、多入口构建、生成脚本语法和差异检查；未执行断言/无头E2E、真实API/数据库消息操作或浏览器验收。
- 后续获授权后人工确认：快速切房身份不闪断、历史追赶不重放一起听副作用、普通发送/分享落盘状态、断网补发/能力暂停及切房后旧回执归属。不能拿编译通过代替这些结论。
